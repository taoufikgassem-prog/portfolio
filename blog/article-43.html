GlideRecordSecure et la sécurité des données dans ServiceNow

Par Taoufik GassemPublié le 29 octobre 2025Mis à jour le 29 octobre 20257 min de lecture

Sommaire

  2. Pourquoi privilégier la version sécurisée

Dans ServiceNow, deux API principales permettent d'interroger et de manipuler les enregistrements côté serveur : GlideRecord et GlideRecordSecure. Comprendre leur différence est essentiel pour écrire des scripts serveur qui respectent les règles de sécurité de la plateforme.

GlideRecord et GlideRecordSecure

GlideRecord est l'API historique et la plus utilisée pour manipuler les enregistrements, mais elle ne applique pas automatiquement les ACL de sécurité définies sur les tables. GlideRecordSecure, à l'inverse, applique ces ACL lors de l'exécution des opérations, garantissant que le script respecte les mêmes règles de sécurité que l'interface utilisateur.

Pourquoi privilégier la version sécurisée

Utiliser GlideRecordSecure dans les scripts qui manipulent des données sensibles, ou qui s'exécutent dans un contexte où l'on souhaite respecter les permissions de l'utilisateur courant, réduit le risque de contournement involontaire des règles de sécurité définies par les ACL.

Le contexte des Script Includes exposés

Ce point est particulièrement important pour les Script Includes exposés côté client via GlideAjax, un sujet traité dans l'article Script Includes : réutiliser la logique serveur dans ServiceNow, où l'absence de vérification de sécurité pourrait permettre un accès non souhaité à des données.

Quand GlideRecord classique reste pertinent

Dans certains contextes, notamment des scripts d'administration système exécutés avec des privilèges élevés et maîtrisés, l'utilisation de GlideRecord classique reste justifiée. La décision doit néanmoins être prise consciemment, et non par simple habitude ou méconnaissance de l'alternative sécurisée.

Bonnes pratiques de script sécurisé

Une bonne pratique consiste à documenter explicitement, dans le code, le choix entre GlideRecord et GlideRecordSecure et sa justification, afin que les futurs mainteneurs du script comprennent les implications de sécurité associées à ce choix.

Checklist sécurité des scripts serveur

  • Le choix entre GlideRecord et GlideRecordSecure est fait consciemment pour chaque script sensible.
  • Les Script Includes exposés côté client sont particulièrement vérifiés sous cet angle.
  • Les ACL des tables concernées sont testées en conditions représentatives.
  • Les choix de sécurité sont documentés dans le code pour faciliter la maintenance.
Utiliser GlideRecord sans réfléchir à GlideRecordSecure peut ouvrir des accès non intentionnels à des données protégées par ACL.

Conclusion

Le choix entre GlideRecord et GlideRecordSecure a un impact direct sur la sécurité des données manipulées par un script ServiceNow. Une attention particulière à ce choix, en particulier pour les scripts exposés côté client, renforce significativement la robustesse de la configuration.
