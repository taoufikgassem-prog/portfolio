Client Scripts et UI Policies dans ServiceNow

Par Taoufik GassemPublié le 24 septembre 2025Mis à jour le 24 septembre 20257 min de lecture

Sommaire

  2. Les UI Policies
  3. Quand utiliser l'un ou l'autre

  5. Checklist de choix
  6. Conclusion

Client Scripts et UI Policies permettent tous deux d'agir sur le comportement d'un formulaire côté navigateur dans ServiceNow, mais ils répondent à des besoins différents. Bien choisir entre les deux facilite la maintenance de la configuration.

Les Client Scripts

Un Client Script est un script JavaScript exécuté dans le navigateur de l'utilisateur, déclenché par des événements comme le chargement du formulaire, la modification d'un champ, ou la tentative de soumission. Il permet des comportements dynamiques complexes, comme des calculs en temps réel ou des appels à des données serveur via GlideAjax.

Les UI Policies

Une UI Policy permet de définir, sans écrire de code, des comportements conditionnels sur un formulaire : rendre un champ obligatoire, le masquer ou le rendre en lecture seule selon la valeur d'un autre champ. Cette approche déclarative est plus simple à maintenir qu'un script pour des besoins standards.

Quand utiliser l'un ou l'autre

La règle générale consiste à privilégier une UI Policy chaque fois que le besoin peut être couvert par ses fonctionnalités déclaratives, et à réserver le Client Script aux comportements plus complexes que l'UI Policy ne peut pas couvrir, comme des calculs personnalisés ou des interactions avec le serveur.

Combiner les deux approches

Il est fréquent de combiner UI Policies pour la logique de visibilité simple et Client Scripts pour des comportements plus élaborés, à condition de garder une vision d'ensemble claire pour éviter les comportements contradictoires entre les deux mécanismes.

Limites du scripting côté client

Les Client Scripts et UI Policies agissent uniquement côté client : ils ne remplacent pas les contrôles de sécurité ou de validation qui doivent être appliqués côté serveur, par exemple via des Business Rules ou des ACL, un point essentiel à retenir pour ne pas se reposer uniquement sur des contrôles côté navigateur.

Checklist de choix Client Script / UI Policy

  • Le besoin est d'abord évalué pour vérifier s'il peut être couvert par une UI Policy déclarative.
  • Un Client Script est utilisé uniquement lorsque la logique dépasse les capacités d'une UI Policy.
  • Les contrôles de sécurité critiques sont dupliqués côté serveur, pas seulement côté client.
  • La combinaison des deux mécanismes est documentée pour éviter les comportements contradictoires.
Ce qui est validé uniquement côté client peut toujours être contourné : les contrôles critiques doivent exister aussi côté serveur.

Conclusion

Client Scripts et UI Policies sont complémentaires pour personnaliser le comportement des formulaires dans ServiceNow. Privilégier l'approche déclarative des UI Policies, tout en réservant le scripting aux besoins réellement complexes, facilite la maintenance à long terme de la configuration.
